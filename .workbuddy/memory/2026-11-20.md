## 直播卡顿日志分析（未改代码，待 A/B 验证）

现场日志：`playlist rewritten: 8片->6片 ... cache=4` 与 `LivePlayerWidget 卡顿 1.4~2.8s 后恢复 源(1)` 一一对应，周期约 3.3~4.8s；卡顿时长≈一个分片(2s)。relay access log 显示 `/liveseg` 400KB `send=0ms`、`/live.m3u8 start=0ms`、全 200、无 404/502/看门狗换源/代理降级 → 服务端与源不是瓶颈。

**结论（高置信）**：`9d225fe feat: proxy`（11-18 引入的进程内 HlsLocalProxy）造成结构性缓冲饥饿。窗口被两级压缩：

- relay `LIVE_LIST_SIZE=12`(24s) + `LIVE_HIDE_TAIL=4`(隐藏最新4片≈8s) → 对外 8片
- 本地代理 `_playlistKeepSegments=6`(裁头) → 播放器只拿到 6片/12s，尾部仍落后实时约 8s
- `fetchPlaylistText` / `fetchSegmentBytes` 让录制与播放器共用这同一份 6片窗口；6 片是按录制锚点稳定性选的，对播放器太浅
- 播放器播到窗口尾(seg02556)后，下一片(seg02557)还被 relay 的 HIDE_TAIL 藏着，需等 ffmpeg 再产 1 片(~2s)才浮出 → 空缓冲等待 ≈2s，即观测到的周期性卡顿

relay 的 HIDE_TAIL=4 原本是为「mpv 直连 relay」设计的抖动吸收垫；插入本地代理后两级机制叠加，垫子变成结构性延迟。

**验证**：临时让播放器直连 relay（跳过 `HlsLocalProxy.prepare`）A/B；若卡顿消失即坐实。

**修复方向**：两级协同——relay HIDE_TAIL 4→1~2，本地代理 keep 6→8~10；或录制/播放器用不同窗口；或录制未开启时禁用代理（少一跳、无裁头副作用）。

### A/B 验证结果（10:04~10:10，翡翠台源1，tv 端）
- A 组直连（注释 prepare）：周期性卡顿完全消失，仅起播卡 1.5s。

### 重要修正：裁头不是唯一根因，真正缺的是「窗口预热」（10:24~10:30）
- 用户编译装机后卡顿**依旧**（新日志格式确认裁头代码已生效）：`8片 seq=... cache=4~5`，每隔 3~4s 卡 1~2.4s，中间有一次 16s 空档不卡（间歇性）。

### 预热增强：填不满窗口的三个原因（10:36~10:45）
- 装机后日志：预热**确实起效**（卡顿从每 3~4s → 每 16~93s），但 cache 始终 5~7、填不满 8 片窗口，残余卡顿是偶发回源慢。warmup 每轮仍有 1~4。

## relay ffmpeg 进程与并发 replay 机制（11:49）
- **ffmpeg 进程为何常驻**：`/live.m3u8` 每会话起一个 ffmpeg（`_live_session` Popen），空闲 60s（LIVE_IDLE_SECONDS）或进程退出才回收（reaper 每 15s），上限 4 个（LIVE_MAX_SESSIONS）。换源即杀同 dev 旧会话（宽限 10s）。所以后台看到 ffmpeg = 活跃转码会话，属正常。
- **连续 2-3 条同一请求 = 会话建立期的并发竞态**，不是异常：
  - 服务端 ThreadingHTTPServer（relay.py:990），每请求一个线程；
  - 会话创建在 `_sessions_lock` 内按 sid=md5(src) 复用（:898-899），这部分能合并；
  - **但 `_probe_resolution`（分辨率探测，ffmpeg -t 1，耗时数秒）在锁外**（:900-911），`s["probed"]` 检查无保护；
  - 首个请求建会话后释放锁 → 去 probe（慢）；第 2、3 个并发请求进锁发现会话已存在直接复用，但 `probed` 仍 False → **各自又跑一次 probe**；
  - 三线程同时 `_wait_ready`（等 out.m3u8，0.3s 轮询，:723-735）→ 首播延迟被放大，且 probe 重复拉流浪费入站带宽/计费。
  - "等一会才合并"= 会话就绪后（`probed=True` + 列表生成），后续请求走复用分支（:639-644）只更新 used，日志不再刷。
- App 端触发：mpv open 本地代理 URL → 代理回源 relay `/live.m3u8`（首播 + 看门狗 reload 都会重新 open）。首播失败/慢时 mpv 或上层重试会连发多条。
- 潜在优化（未改，需先 A/B）：把 probe 移进 `_sessions_lock`，或在 s 里加 `_probe_future`/`probing` 标志做 single-flight，避免会话建立期重复探测。改 relay 要部署 yuntu（先改源码再部署）。

## 设备类型判定规则填错字段的排查（17:34）
- 用户后台给「多路开关」配规则优先级 22（想压过插座 20），但「小米米家智能开关（双开单控）」仍被识别成插座。
- **根因：规则字段填成 `entity_id`，值却是 model**。用户填 `entity_id contains zimi.switch.dhkg02`，但该值是 device.model；真实 entity_id 是 `switch.zimi_cn_1065542586_dhkg02_on_p_2_1`/`_p_3_1`，根本不含 `zimi.switch.dhkg02` 子串（真实是 `zimi_cn_1065542586_dhkg02`）→ 规则永不命中 → 落 socket 默认 `domain eq switch`。
- 判定引擎 `deviceTypes.js:classify()`：先比 specificity（命中规则条件数），相同才比 priority。这里两者都 spec=1，若命中 22>20 必胜——所以纯粹是没命中，不是优先级问题。
- 复现验证（用真实实体数据跑 `dt.classify` + includeAll）：`entity_id contains zimi.switch.dhkg02`→socket；`device.model contains zimi.switch.dhkg02`→multi_switch；`entity_id contains dhkg02`→multi_switch。用户自行在后台改成 `device.model` 后判定成功，闭环。
- 后台配置存 `datas/admin/deviceTypes.json`（覆盖层，admin UI 保存即时生效，无需重启服务）。field 可选：entity_id / name / state / domain / attr.* / device.model 等。排查手法：HA 真实 entity_id 从 `datas/realtime/events.jsonl` 的 entityId 字段取；判定用 `node` 引 `server/deviceTypes.js` 本地复现（脚本放仓库根，勿放 /tmp——Git Bash 会映射到 E:\tmp）。
