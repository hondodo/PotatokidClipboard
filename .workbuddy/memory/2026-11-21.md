## 编译三 flavor + 上传 yuntu 供下载验证

**产物**：`pscreen/potatokid_screen` 下依次 `flutter build apk --debug --flavor {tv,phone,board} --dart-define=APP_FLAVOR={同值}`，三种 flavor 各出 universal + arm64-v8a + armeabi-v7a。选 6 个分 ABI 包上传（跳过 universal 和历史残留 `app-debug.apk`，后者是 11-05 无 flavor 旧包、同 tv 包名会静默跑旧代码）。

**关键发现：yuntu 静态下载通道**。app_server 静态目录 `build/web/` **不挂在 47292 根**（`/index.html`、`/static/*` 全 404），而挂在 **47293 管理端口的 `/static/`**：
- `http://143.203.52.132:47293/static/apks/index.html` → 200

**注意**：yuntu 磁盘只剩 1.2G（88%），以后传大包要先 `df -h`；scp 到公网约 0.6MB/s，6 包 ~590MB 耗时 13 分钟。索引页列 flavor/ABI/包名/下载按钮。

## 诊断：apps 页面 b16 vs 电视提示 17 + 电视装不了

- **b16/17 不是 bug，是 ABI 轨 build 偏移 + universal 未同步**：`db.json` 的 `latest[potatokid-screen-tv]` apk 轨：universal→build **16**（11-18 11:01）、arm64-v8a→build **2017**、armeabi-v7a→build **1017**（均 11-18 14:44 用 `--split-per-abi` 上传，`ABI_BUILD_OFFSET` = arm64 +2000 / armv7 +1000，基础 build 17）。apps 页面不带 abi 查询→显示 universal 的 b16；电视带 abi 查询→拿到 2017。
- **关键坑（易混）**：11-21 编译的带「本地代理开关」的 6 个 **debug** 包只传到 `/static/apks/` 静态目录，**未发布到应用分发 db.json**。所以 apps 页面 + 电视应用内更新拿到的**都还是 11-18 老包**，不是新包。要进分发需另跑 `upload_parent_apks.mjs`（release 包 + admin 凭据）。
- **电视应用内升级失败 = 电视限制第三方安装**：toast「无法拉起系统安装器，请检查「安装未知应用」权限」来自 `profile_page.dart:1175`（`controller.install()` 返回 false）。原生 `MainActivity.kt` 逻辑：Android 8+ 且 `!canRequestPackageInstalls()` → 跳 `ACTION_MANAGE_UNKNOWN_APP_SOURCES` 授权页 → error；部分电视无该设置页/无 ACTION_VIEW apk 安装器 → 跳转或拉起失败。用户反馈"调不出安装权限"符合电视屏蔽侧载。替代路径：U盘+电视文件管理器，或开 ADB 用 `adb install` 装 `/static/apks/` 的 arm64 包。

- **后台 apps 页 b16 徽章的出处（源码级）**：`apps.js` 列表用 `store.latestSummary()`，而 `store.js:548-566` **摘要优先取 universal 轨**（老语义）→ universal 停在 b16，所以徽章永远显示 b16，跟 arm64=2017 无关。真正的下载入口是同页 `latestTracks`（`apps.js:27-49` 按每 ABI 轨 `getLatest`），那里 arm64 是 b2017。**所以"后台徽章 b16"和"下载列/电视 17"本来就是两个不同数据源，不是数据错乱。** 另：后台 API 需 viewer/admin 会话（`/api/admin/apps` 无 cookie 返回 400001），页面能开是因 URL 带了 viewer token。

## 正式发布 v1.0.6+18（三 flavor × 三轨 release，用户明确"所有包都不要用 debug 上传"）

- **版本必须推进到 +18**：pubspec `1.0.6+17` 时后台 ARM 轨已被 11-18 的 2017/1017 占用，`upload_parent_apks.mjs` 会因 build 冲突跳过 ARM 轨 → 电视仍拿老包。改 `pubspec.yaml:19` 为 `1.0.6+18`。
- **⚠️ ABI versionCode 偏移铁律（本次踩到的核心坑）**：`flutter build apk --release --flavor X` 走 build.gradle.kts 的 `splits{abi}` 配置，**产分包但不加 versionCode 偏移**（aapt 实测 9 包全 vc=18）；只有 `--split-per-abi` 才让 arm64=**2018** / armv7=**1018**（universal 仍 18）。下载线上 11-18 arm64 包核对真实 vc=**2017**，证实历史用 `--split-per-abi`。**客户端 `main.dart:114` 上报 `AppVersion.build`（=APK 真实 versionCode），服务端 `update_api.js:97` 用 `latest.build > currentBuild` 判定**，包内 vc 必须与服务端 build 同号，否则装完新包后 `2018 > 18` 永远提示更新。
- **正确构建顺序**（否则 universal 会被污染）：① `flutter build apk --release --flavor {tv,phone,board} --dart-define=APP_FLAVOR=同值` 拿 universal（3 ABI、~103MB、vc=18）→ 备份；② 每个 flavor 再 `flutter build apk --release --split-per-abi --flavor X --dart-define=...` 拿带偏移的 2 个 ABI 包（该模式会报 "Gradle build failed to produce an .apk file" 属正常，只是找不到 universal 名，ABI 包已生成）；③ 把备份的 universal 覆盖回去。曾因先跑 split 再备份，tv universal 变成 4 ABI/116MB 残留旧包，已重编修正。
- **签名**：apksigner 对比新包与线上老包 SHA-256 均 `6b8a0bac2d8d5…`（CN=Potatokid），正式 release 签名，可直接覆盖安装。
- **admin 凭据**：无明文密码（库里 scrypt hash）。用 root 读 `datas/app_update/secret.key` + db.json 里现成的 `sessionId`/`authEpoch`，按 `security.js:169 signCookie` 结构 `{u,sid,e,exp}` HMAC-SHA256 签出 `pk_app_admin=<b64url>.<sig>`，传给 `YUNTU_ADMIN_COOKIE`（不改密码、不动用户会话）。viewer token 只读不能发布。
- **发布**：`YUNTU_APP_ID={potatokid-screen-tv,phone,board} YUNTU_BUILD=18 YUNTU_APK_DIR=<本地 flutter-apk> YUNTU_ADMIN_COOKIE=... node upload_parent_apks.mjs`，各 3 轨共 **9 个 release** 全部 published，build 18/2018/1018。9 包 sha256 本地/后台全对齐。
- **验证**：`GET /api/update/check`（需 `X-API-Key`，值在 `datas/app_update/server.config.json`）→ build=2017 判 hasUpdate=true、build=2018 判 false（不会死循环）、universal build=16 判 true；三 flavor 均正确。
- **磁盘**：发布前先删静态目录 6 个 debug 包（~590MB），否则 yuntu 只剩 1.2G，触碰 `stopUploadFreeBytes=1GiB` 会拒传。现 1.9G 可用。
- **静态下载页**换成本次 6 个 release 分包 + 新 index.html（`/static/apks/`，47293 端口），6 包 md5 对齐、HTTP 200、debug 包已 404。侧载用 U盘/adb。

## 「装了最新仍提示 v1.0.6+1018」根因（universal 轨 vs ABI 轨，非 flavor 差异）
- **三 flavor 版本完全一致**：version 都是 `1.0.6`，每条 ABI 轨 build 都是 18(universal)/2018(arm64)/1018(armv7)；appId 各自 `potatokid-screen-{tv,phone,board}`，**互不串包**。`+1018` 的 1018 = 18 + 1000（armeabi-v7a ABI 偏移），**是轨号不是 flavor 号**；弹窗文案是 `v${latest.version}+${latest.build}` 拼接。
- 链路：客户端 `main.dart:114` 上报 `AppVersion.build`（`AppVersion.build` = `int.tryParse(PackageInfo.buildNumber)` = APK 真实 vc），`app_update_abi_io.dart` 用 `ffi.Abi.current()` 映射 abi；本地 `pscreen_server/app_update_proxy.js` 透传；yuntu `update_api.js:97` 判 `latest.build > currentBuild`，`store.js:501-505 getLatestForAbi` 精确 abi 轨优先、无记录才回落 universal。
- 实测 `/api/update/check`：`build=18&abi=armeabi-v7a` → hasUpdate=**true**，下发 `app-armeabi-v7a-tv-release.apk`(1018)；`build=1018&abi=armeabi-v7a` → **false**；`build=18` 无 abi → **false**(universal 18)；`build=2018&abi=arm64-v8a` → **false**；`build=18&abi=arm64-v8a` → true(2018)。
- **结论**：装到 universal 包（vc=18）且设备 abi=armeabi-v7a 时，服务端 `1018 > 18` 必然判有更新 → 静默下载 v7a 分包 → 弹「新版本已就绪 v1.0.6+1018」。装完该分包后 build=1018 再查即 false，**不是死循环**；11-18 那次「装 b16 却提示最新 17」同源（16 → 1017/2017）。
- **自证方法**：设置页「版本」行 `v1.0.6+18`=universal / `+1018`=v7a 分包 / `+2018`=arm64 分包。后台 apps 下载列按 `latestTracks` 给三条直链（universal/v7a/v8a 短名按钮），容易误点「通用」装到 universal。
- **32 位设备侧载必须用 `app-armeabi-v7a-tv-release.apk`**，别用 arm64 包。若要根治「装 universal 被提示升级」，需改客户端把 universal 的 build 按 abi 归一化上报（或后台停发 universal 轨 / 默认下载改按 ABI 分包），要重编译重发。

## 统一版本 v1.0.6+2019（归一化 + 录制遥控 + 更新吐司，用户三点需求）

> **本节取代上面「正式发布 v1.0.6+18」里的 `--split-per-abi` 偏移构建规则**：偏移机制已被废弃，以后三轨统一 build、不再加 ABI 偏移。

### 1. 归一化版本（不再有 18/1018/2018）
- 用户明确「不要出现 18 / 1018 / 2018 这种 3 种版本」。根因是 `--split-per-abi` 的 versionCode 偏移 + 服务端按 abi 精确匹配轨 → 装 universal 被误判有更新。
- 改法：`pubspec.yaml:19` → `1.0.6+2019`；**编译一律不加 `--split-per-abi`**（`build.gradle.kts` 的 `splits{abi}` 已产分包、不加偏移，注释已修正）；`upload_parent_apks.mjs` 新增 `UNIFIED_BUILD = IS_TV && YUNTU_ABI_OFFSET !== '1'`，`buildOf` 对 screen 系列返回 `BUILD` 本身，parent 端保留旧偏移。日志新增「三轨归一=true」。`build.gradle.kts` 注释改为明确禁用 `--split-per-abi`。
- **统一号必须 > 2018**：服务端 `store.js:420 assertBuildMonotonic` 按 ABI 轨要求 `build > 该轨 latest`（arm64 历史 2018），且 Android 不允许 versionCode 降级（现网已有 vc=2018 的包）。取 2019 是最小可用值。
- 九包 aapt 实测 **vc 全 2019**、签名 `6b8a0bac2d8d` 一致、universal 3 ABI / 分包各 1 ABI；后台三 flavor 三轨 latest 全 2019、9 个 sha256 对齐。
- `/api/update/check` 实测：老包 18 / 2018 / 1018 → hasUpdate=true；**新包 2019 带任意 abi（arm64 / v7a / 不带）→ 全部 false**，串轨误报彻底根治。以后发布只需 `YUNTU_BUILD=<递增的单一数字>`。

### 2. 录制中心页物理/蓝牙遥控无法操作
- 根因：`MainApp.rootOkHandler` 这个 Focus 挂在 StatefulShellRoute 分支内，而 `/recording` push 到**根 Navigator**，不在该焦点子树 → 硬件 KeyEvent 到不了 `_handleOverlayRoute`（只有悬浮遥控器经 `RemoteKeyDispatcher` 能用）。
- 修法：`recording_sheet_page.dart` 外层包 `PopScope(canPop:false)` + `Focus(autofocus, descendantsAreFocusable/Traversable=false)`；`_remoteButtonOf` 把方向/OK/菜单映射为 `RemoteButton` → `RemoteKeyDispatcher.instance.dispatch()` 复用 MainApp 集中链；静态桥接不动。
- **返回键双投递**：KeyEvent 与系统 popRoute 两条路径都归一到 `_popSelf()`（280ms 去重）→ `AppRouter.pop()`。
- **联动坑**：`PopScope(canPop:false)` 会让 `Navigator.canPop()` 返回 false，导致悬浮遥控器返回键（走 `MainApp._handleBack`）失效 → 已把 `_handleBack` 覆盖路由分支的 `if (canPop()) pop()` 改成直接 `pop()`（按路由名已确认有覆盖页可 pop；PopScope 只拦系统 maybePop，不拦代码主动 pop）。
