## 七、实体下拉菜单被滚动/失焦误关（已修复并部署，2026-11-16 上午续）

用户反馈：ESP 控制项弹窗里的实体下拉**展开后，滚轮滚动或拖动下拉滑块都会把下拉关掉**，导致无法选中。

### 1. 根因（三处叠加）

1. **滚动监听用了捕获阶段且无过滤**：`window.addEventListener('scroll', close, true)` —— `capture=true` 会收到**任何元素**的滚动事件，包括下拉菜单自身。菜单一滚就被当成「页面滚了」→ `close()`。
2. **blur 兜底误伤**：拖动菜单滚动条时浏览器会把焦点从 input 甩到 body，`input.blur` 触发 → 150ms 后 `close()`。旧代码靠 `openAt` 时间戳（400ms 窗口）兜底，但拖动超过 400ms 一样中招。
3. **`resize`/`scroll` 都直接 close**：菜单是 `position:fixed`，本来只需重新定位。

### 2. 修法（`pscreen_server/web/admin.html` 的 `createEntityPicker`）

- **滚动不再关闭，改为重新定位**：`scroll` 捕获监听里先判断 `menu.contains(event.target)` → 是菜单自身的滚动就直接 return；否则 `positionMenu()` 让菜单跟随输入框。`resize` 同样改成 reposition。
- **关闭条件收敛为「焦点真正离开」**：删掉 `input.blur` 定时关闭，改为
  - `input.focusout` + `document.activeElement` 判定：`activeElement` 是 `document.body`（焦点散失，点滚动条/空白）→ **不算离开，不关**；落在 wrap/menu 内 → 不关；落在别处 → 关。
  - `document.focusin`（target 不是 body 且不在 wrap/menu）→ 关。
  - `document.mousedown`（点在 wrap/menu 外）→ 关。
  - 新增 `Escape` → 关。
- **`overscroll-behavior: contain`** 挂在 `.entity-picker-menu`：滚到底不把滚动传给弹窗内容，避免连带滚动后菜单跑位。
- **document/window 级监听统一挂 `AbortController`**，弹窗关闭时 `dispose()` 里 `listeners.abort()`，不再残留监听。
- **显式滚动条样式**（`::-webkit-scrollbar` width 10px + 可见 thumb）：系统 overlay 滚动条默认不显示，用户看不到「这里能拖」。
- **菜单高度** `max-height: min(60vh, 460px)`（原固定 300px），468 个实体不再要滚太久；`positionMenu()` 的翻转判断同步改成读同一个上限。

### 3. 顺带修的关联 bug：中文搜索搜不到

- 输入框里还留着上次选中的 entity_id，用户接着打字会变成「switch.xxx洗衣机」拼接串 → 拿整串去搜必然 0 结果。
- ⚠️ **不能用 keydown 里 `input.select()` 的老办法**：中文/IME 输入走 `beforeinput(insertText)`，**不派发 keydown**（Playwright `keyboard.type` 中文同样不触发 keydown，实测确认），所以 select() 方案对中文无效。
- **采用前缀剥离**：`input` 事件里若 `input.value.startsWith(current) && 长度 > current.length` → 剥掉旧 id 前缀，搜索词与输入框内容都变成干净的新输入部分，光标移到末尾。IME 友好。

## 八、HA 实体库房间筛选串家（已修复并部署，2026-11-16 下午）

用户反馈：实体库里选中「棠德304 → 客厅」，右侧却返回**所有家庭**「客厅」下的内容。

### 1. 根因（前端 `renderHaTree` / `filterHaEntities` 两个 bug）

1. **点房间只设了 `room`，没设 `home`** —— `filterHaEntities` 里 `if (room && entity.room !== room) return false;` 只按房间名匹配。而「客厅」在 3 个家都存在（金科1204=161、薯仔4号的家=4、棠德304=43），必然串。同一 bug 还导致点房间后标题不显示家名。
2. **变量遮蔽** —— `for (const room of homeItem.rooms)` 把外层 `const { home, room } = state.haFilter` 的 `room` 遮住了，`home === homeItem.name && room === room.name` 变成 `room === room.name`（拿对象比字符串）→ **恒为 false**，所以选中的房间节点永远不高亮。

### 2. 修法

- 新增共享函数 `haEntityRoom(entity)`（口径 `room → areaName → '未命名区域'`，与后端 `ha_catalog.js` 的分组口径一致），实体库表格与 ESP 选择器说明文字统一用它。
- **房间筛选必须跟着家一起生效**：`if (room) { if (!home) return false; if (haEntityRoom(entity) !== room) return false; }` —— room 存在而 home 为空是非法组合，直接排除，避免列出所有家的同名房间。
- **房间节点带上所属家**：`roomNode(homeName, roomName, count, isActive)`，点击时同时设 `home` 和 `room`；再次点击同一节点才清空。
- **表格加「家」列**（原来只有「房间」列，本身就看不出归属），表头 6→7 列，`colspan="6"` → `colspan="7"`（只改 HA 表的三处，traffic 表的 colspan=6 保持不动）。
  - ⚠️ 第一次改漏了 `tr.append(...)` 里没加 `homeTd`，导致列错位（家列显示成房间名）——第二版才补上。**加列时表头、colspan、行 append 三处必须同步。**

## 九、HA 实体库表头透明重叠 + 状态列无限撑宽（已修复并部署，2026-11-16 下午）

用户反馈两张问题：① 表头「名称 entity_id 域 家 房间 状态」这一栏透明，滚动时文字重叠；② 状态列无限长，把前面的内容宽度挤短（两个「只看」都不勾时必现）。

### 1. 根因

1. **表头透明**：`th` 的背景是 `rgba(255,255,255,.025)`（几乎全透明），而 `th` 是 `position:sticky; top:0` 悬浮在表格上方 → 下方行的文字直接透过来和表头文字叠在一起。这是**全局样式**，所有 tab 的表格都有此问题（本次一并修好）。
2. **状态列无限宽**：HA 的 `state` 字段可能是 sensor 的长属性串（如 `0,0.48656,8,8,64,20,0,0,...`），表格是 `table-layout:auto`，这列按内容撑开 → 前面「名称」列被压成**一字一行**（截图里「金卧/白」「醉白」竖排就是这个现象）。

### 2. 修法

**表头不透明**（全局 `th`）：
- `background: rgba(255,255,255,.025)` → `#16202a`（实体色，alpha=1）
- `border-bottom` 改为实体色 `#22303d`（原来用 `--line` 半透明色，滚动时也会透）
- `z-index: 1` → `2`
- 顺带把 `.program-preview-wrap th` 里原本单独写的 `background:#16202a` 去掉冗余（现在全局统一了）。

**表格固定布局**（仅 `.ha-table-wrap`）：
- `table-layout: fixed` + `min-width: 1100px`（auto 布局下任何一列都能被内容撑开，fixed 后按 th 声明的宽度分配，互不影响）。
- `td { overflow:hidden; text-overflow:ellipsis; white-space:nowrap }`；空态行 `.empty` 恢复 `white-space:normal`。
- `th` 宽度重新分配：名称(自适应234) / entity_id 250 / 域 92 / 家 110 / 房间 110 / 状态 170 / 操作 164。
- 状态列用 `.ha-state-cell`（flex + ellipsis）包住，**完整值放 `title`**，`td` 与内部 `.status-text` 都设 `min-width:0` 否则 flex 子项撑不开。
- `entity_id` 长 id 允许折行：`.ha-id-text { display:block; white-space:normal; word-break:break-all; max-height:2.8em; overflow:hidden }`（最多两行）。

- 操作列 `.ha-actions-td { overflow:visible; white-space:normal }`（按钮不能被裁）。

### 4. 经验

- **`position:sticky` 的表头背景必须用实体色**，半透明色（哪怕只有 0.025 alpha）会让下方内容穿透叠加。`border-bottom` 用半透明的 `--line` 同样会透。

- **长 id 用折行（最多 N 行）优于省略号**，因为 id 是要复制/对照的关键信息。

## 十、表格文字不该靠悬停 title 才看全（已修复并部署，2026-11-16 下午）

用户反馈：「支持它们换行，不要用鼠标放上去才显出所有文字。这是一个反人类的设计」。

### 1. 问题

上一轮（九）为了钉住状态列宽度，给 HA 实体库表格加了 `text-overflow:ellipsis` + `title` 提示。用户认为**悬停提示是反人类设计**——看表要额外操作才能拿到信息。

### 2. 修法：全部完整换行显示，不要省略号、不要 title

- `.ha-table-wrap td { overflow:visible; white-space:normal; overflow-wrap:break-word }`（去掉 ellipsis / nowrap / overflow:hidden）

### 4. 经验（重要）

- **「省略号 + 悬停 title 显示完整值」是反人类设计**：读表的人要额外操作才能取到信息。

- `overflow-wrap:anywhere` 会把 CJK 任意切断，中文场景用 `break-word`。

## 十一、ESP 显示屏配置与显示规划原型（仅规划，未落地代码，2026-11-16 下午）

### 1. 现状调研（esp_devices/）

- 固件 `esp_devices/firmware/potatokid_esp/potatokid_esp.ino`：ESP32-S3 + SH1106 128×64 OLED（I2C 地址 0x3C，SDA=GPIO8/SCL=GPIO9），物理按键 GPIO4/5/6（按下=低），数组预留 `btnLabel[8]`。
- `oledShow(title,l1,l2,l3)`：helvB10 标题基线 y=13、分隔线 y=17，6x10 三行基线 31/44/57；中文用 `u8g2_font_wqy12_t_gb2312` + `drawUTF8`（`fitUtf8` 按字符截断，中文 3 字节）。
- 现有屏幕只显示 WiFi/IP/srv/信号、按键 toast、OTA 进度——**没有「页面」概念**。
- 服务端 `admin.js` 白名单是**平铺**的 `espActions[]`（`{id,name,entityId,action,button,enabled}`），接口 `GET /api/device/esp/actions?format=text` 返回 `button|name|entityId|action|id` 每行一项；`POST /api/device/esp/press {deviceId,button}`。
- 结论：**引入「页面 Page」作为配置单元**即可支持多设备复用同一组按键，不需改硬件/固件架构。

### 2. 规划方案（写进两个 HTML 的说明里）

- **数据模型**：`machines.json` 增加 `espPages[]`，每页 `{id,name,icon,display:[{entity,fmt}],buttons:[{slot,label,kind:'ha'|'sys',act,entity}],loop,idle}`。
- **行为分两类**：HA 动作（toggle/turn_on/turn_off/run/数值±）与系统动作（下一页/上一页/回首页）——翻页不新增硬件按键，把某槽位设为「下一页」即可。
- **显示分层**（128×64 只能 5 行）：顶部系统状态栏（页码+WiFi，固件固定绘制）/ 标题=设备名 / 主状态=开关或当前值（最大字号）/ 副状态=多字段 join 成一行 / 底部按键提示条。
- **职责划分**：服务端把 HA 实体状态翻译成屏幕文本（on→开、42.5→42°C），ESP 只渲染文本——不需要 JSON 库，中文字库已够。
- **8 个屏幕状态**：常规页×2、按键反馈 toast 2.5s、WiFi 断线、配网、OTA 升级、服务端不可达、未配置。区分「WiFi 断了」与「服务端失联」（顶部图标不同）是关键。
- **用户关心的信息优先级**：联网状态 > 当前设备是什么 > 现在什么状态 > 关键参数 > 按键现在能做什么 > 操作反馈；不显示 entity_id/IP/RSSI/日志。

### 3. 关键约束（原型调试中实测发现）

- canvas 里中文渲染高度比 U8g2 点阵字体大：用 15px/13px 中文 + 行距 13px 会重叠，最终用 **标题 10px@基线22 / 主状态 12px@基线38 / 副状态 8px@基线50 / 按键条 y54~64@基线62**，分隔线 y25。
- **底部按键提示条 128px 摆 5 个按键 → 短标签最多 2 字（推荐 1 字）**：「5›」这种单字符最稳；完整名称保留在后台和按键 toast 里。
- 副状态第 2 行起服务端 join 成一行（如 `水温42° · 目标45°`），否则底部提示条会被挤掉。

### 4. 产出

- `docs/esp-screen-admin-prototype.html`：三栏（页面列表/配置区/128×64 实时预览），可切页、改名、增删显示行、改按键行为、切系统动作，画布实时重绘。

## 十九、按真实代码做 ESP 屏幕规划可行性分析（2026-11-16 下午续）

### ESP 16MB Flash 分区澄清（已 ssh 部署机核实）
- 「16MB」是**整片 SPI Flash 物理容量**（`FlashSize=16M`），不是某个分区。分区表把它切成多块。
- 编译用 `PartitionScheme=no_fs`，其定义 `~/.arduino15/packages/esp32/hardware/esp32/3.3.12/tools/partitions/no_fs.csv`：
  `nvs 0x9000/20KB`、`otadata 0xe000/8KB`、`app0(ota_0) 0x10000/~2MB`、`app1(ota_1) 0x200000/~2MB`、`coredump 0x3F0000/64KB`。
- **关键：no_fs 只用了前 4MB（末分区止于 0x400000），后 12MB 完全闲置**。boards.txt 里 no_fs 本就是「No FS 4MB (2MB APP x2)」，被用在了 16MB 芯片上。
- 双 app 槽 = 远程 OTA 基础（新固件写空闲槽、失败回滚）；每槽 2MB 是为了装中文字库（默认分区 1.25MB 装不下，huge_app 3MB 但无 OTA）。
- **修正上一轮判断：Flash 不是瓶颈**——当前只用了 4MB、剩 12MB 空闲，将来放大字库/多套资源换用满 16MB 的分区表（app 槽 6MB+）即可，代价仅换分区表需重新 USB 烧录一次。

### home 端热水器实现调研（已读源码，用于反哺 ESP 屏幕规划）
- **数据模型**：`WaterHeaterSummary.tryBuild()`（domain/models/water_heater_summary.dart）从设备全部实体里按后缀聚合：
  - 主实体 `water_heater.*`：`state`=当前模式、`attributes.temperature`=目标温度、`current_temperature`=当前水温、`target_temp_step`=步进(默认0.5)、`min/max_temp`≈35~65℃、`operation_list`=可选模式。
  - 辅助实体按 entity_id 后缀匹配：`switch *_hot_water_recirculation`→预热、`switch *_intelligent_preheat`→定时预热、`sensor *_status_p_2_5`→工作状态、`sensor *_input_water_temperature`→进水温度、`sensor *_water_flow_p_2_9`→水流量、`event *_usage_record_e_4_1`→用水记录、`text *_preheat_timer_p_2_13`→定时编码串。
  - `statusLabel`：关机→「已关机」，否则取 status 实体值、回退到 mode；`hasFault`：fault 非 0/unknown/unavailable 即故障。
- **控制链路**：UI(water_heater_control_panel.dart) → HomeBloc → home_repository_impl.dart 调 HA：
  - 开关 `ToggleEntity`→`setEntityPower`→`<domain>/turn_on|turn_off`（热水器是 water_heater/turn_on|off；预热是 switch/turn_on|off）。乐观更新+失败回滚。
  - 温度 ±/滑杆 → `SetWaterHeaterTemperature` → `water_heater/set_temperature` body `{'temperature': 值}`，先 clamp 到 min/max 再按 step 取整。
  - 模式 → `SetWaterHeaterOperationMode` → `water_heater/set_operation_mode` body `{'operation_mode': 值}`。
- **反哺 ESP 的关键结论**：
  1. 屏幕该显示什么，home 端已经给出答案：目标温度(大字) + 当前水温 + 工作状态 + 预热状态 + 故障；这正好是 ESP 预览里的「标题/主状态/副状态/按键提示」内容来源。
  2. **「+/-」不是新 action 种类，而是同一个 `set_temperature` 带不同数值**（温度 = 当前 ± step）。所以 ESP 不必扩展 `increase/decrease` 服务名——正确做法是让 action 支持**携带数值参数**，服务端仍调 `water_heater/set_temperature`。这比上一轮「扩展 increase/decrease 或建 HA script」的结论更准确、更省事。
  3. **服务端契约缺口定位清楚了**：`callHaService(entityId, action)`（admin.js:853）body 固定 `{'entity_id': ...}`，`resolveActionService` 只按 4 类无参 action 解析。要支持热水器必须有「action + 参数（数值/模式串）」的传递通道——这是 P2 要补的核心，且令牌仍留服务端（home 端也是客户端不碰令牌）。

### 设备展示架构决策：按 HA domain 还是按业务设备类型（已读 home 端源码）
- 用户问：这么多设备类型（热水瓶/灯/风扇/空调/投影/空气炸锅/洗衣机…），是按业务类型分别做展示，还是按 HA 分类（switch/button/value/status/传感器）做通用展示？
- **home 端真实做法 = A 打底 + B 增强，不是二选一**：
  - 底层通用：`HaDeviceGroup.group()` 按 HA `device_registry` 把同一物理设备的多实体合成一张卡；**不按 domain 过滤**，全部实体可见（sensor 以值 label、button 展示不交互、unavailable 置灰排末尾）；主实体靠 `_sortWeight`（真灯0>空调/热水器/风扇1>主开关2>其他switch3>数据5）+ `_isMainPowerSwitch`（只认 `_on_p_x_x`/`_power` 后缀，不用显示名）挑。
  - 上层专用：`lib/features/home/domain/models/` 有 **14 个 XXXSummary**（water_heater/kettle/fan/washer/projector/air_fryer/fridge/rice_cooker/socket/water_purifier/range_hood/multi_switch/lock/home_climate），每个靠「domain + entity_id 后缀」识别关键实体（如热水器 `_hot_water_recirculation`/`_status_p_2_5`；洗衣机 `_status_p_2_2`/`_mode_p_2_3`/`_left_time_p_2_10`），出专用详情面板。`device_detail_page.dart` 依次识别这些 Summary 决定渲染哪套面板，门锁优先（安全设备禁用全部控制）。
- **为什么必须两套并存**：HA domain 只能回答「这是什么类型的控制」（灯/开关/数值），回答不了「这台设备的核心信息是哪几项、按钮该怎么分组」——后者是产品语义，米家同一 domain 的不同设备差异巨大。
- **ESP 落地结论**：固件/屏幕保持通用渲染（只认 4 行文本 + 按键槽），**复用 home 端 B 层识别规则但只取「数据字典」**——服务端代读 HA → 按同款后缀规则抽标题/主状态/副状态/按键提示 → 随页面配置下发。专用逻辑只在服务端一处维护；未识别的新设备降级为通用展示（domain + state），不会黑屏。这样新设备接入成本 = 在服务端加一条识别规则，固件零改动。
